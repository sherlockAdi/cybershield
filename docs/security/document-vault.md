# Encrypted document vault, version 1

Files (up to 5 MiB) and filenames are encrypted in the browser with AES-256-GCM. Each file has a fresh random key and IV. Authenticated context binds ciphertext, encrypted metadata and wrapped keys to their document UUID and purpose. The random vault key wraps document keys; a separate password-derived key wraps the vault key. PBKDF2-HMAC-SHA256 uses a random 16-byte salt and 600,000 iterations, fixed in the client. Use a strong unique passphrase: a database thief can attempt offline password guesses.

The password, plaintext files, plaintext filenames and unwrapped keys are never sent to the API. Keys are held in component memory, not local/session storage. Locking, leaving the page or the 10-minute unlock limit removes UI references; this is not a guaranteed secure memory wipe in a JavaScript runtime. No server-side password reset/recovery exists. Losing the vault passphrase means losing access. Account login/MFA reset does not recover vault keys.

Each account has a separate vault within each organization. Authenticated routes require current membership and MFA; only the uploader can list/download/share/delete their documents. Organization administrators receive no alternate decrypt key. The database retains ciphertext, encrypted key envelopes, sizes, owner IDs and timestamps. Each vault is limited to 100 documents / 100 MiB of ciphertext. Partial uploads count toward this quota and can be deleted by their owner. Backups include ciphertext and may retain deleted encrypted files until backup retention removes them.

Public links contain a random 256-bit capability token and document key in a URL fragment. The fragment is not transmitted as part of HTTP URLs. The share page removes it from the visible URL and uses POST bodies for capability requests; the decryption key never enters those requests. Only the token hash is persisted. Tokens expire 1 or 30 minutes after generation using database time, can be revoked, and never disclose the wrapped vault/document key. Every chunk request checks expiry, revocation, uploader membership/account state and document readiness. The browser also checks the deadline and revalidates before offering the download. The share page has no third-party resources or analytics. API responses use no-store and the dashboard uses no-referrer.

Expiry is access control, not remote erasure. Recipients can retain plaintext or encrypted content plus its key received before expiry. Revocation cannot retract data already delivered. Anyone possessing the full link can forward it; the owner must share it privately. Deleting a document removes its live chunks and links; encrypted backups have independent retention.

This design protects document contents against passive database/disk/backup access, subject to password strength and cryptographic assumptions. It does NOT protect against an active server administrator deploying malicious JavaScript, a compromised browser/extension/device, an XSS vulnerability stealing an unlocked key, or a recipient sharing the link/key. An absolute guarantee against active server compromise requires an independently distributed and verified client, not solely a website served by that server. Do not market this as total security or DRM.

Tests cover wrong passwords, AAD mismatch, modified ciphertext, private owner/tenant isolation, incomplete uploads, immutable finalized chunks, expiry/revocation/removal, absent plaintext/keys in persistence, HTTP auth/MFA session/CSRF/origin checks and chunk parser limits. Deployment uses the existing additive migration pipeline and encrypted-data database backup. No external security audit is claimed.
